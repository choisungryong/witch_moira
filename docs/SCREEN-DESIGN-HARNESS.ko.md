## 1. 한 장 요약

**진단.** 지금까지의 화면 작업은 "있는 틀에 정보 줄을 더하는" 식이었다. 가장 최근 예인 켠 판의 성장 카드(RS3)는 정보는 맞지만 같은 크기의 글 상자 셋이고, 카드 아래 40%가 비어 있고, 단추 셋이 모두 "서약 선택"이다 [봄: `_local/shots/rs3/cards-1920x1080/boon_spells.normal.1920x1080.png`, `boon_spells.long.1920x1080.png`]. 고르는 순간의 기대·드러남·확정의 감정이 화면 어디에도 없다. 첫 화면 겸 캐릭터 선택도 같다: 어두운 창 하나에 작은 초상 칸, "○○으로 시작" 글 단추 셋, 설정 토글·음소거·종료·보관함이 한 판에 섞여 있어 **인물이 아니라 단추 목록이 주인공**이다 [봄: `_local/shots/rs0/rs-frost-1080/01-menu.png`, 11-19 22:34]. 원인은 셋이다.
1. **출발점이 기준작이 아니라 기존 틀이었다.** 구성안을 여럿 그려 고른 적이 없다(A4의 목업 12장은 재질 방향을 고른 것이고 화면 구성을 고른 것이 아니다).
2. **화면이 시스템에 묶여 있다.** 성장 선택 화면은 코어 객체(`run`)를 직접 뒤져 그린다. 그래서 시스템이 꺼져 있거나 바뀌는 동안 화면 작업이 기다리거나, 시스템 작업의 끝에 "화면에 줄 하나 더"로 붙는다(2.3절).
3. **화면 하나를 끝까지 데려가는 정해진 길이 없다.** 목적, 조사, 구성안, 사용자 선택, 계약, 구현, 검수, 적용이 문서마다 따로 있거나 빠진다.

**하네스.** 화면 하나는 여덟 단계를 지난다(3절): ① 목적과 감정 → ② 기준작 조사 → ③ 구성안 2~3개(**Godot 시안 장면으로 그린다**, 3.3절) → ④ 사용자 선택 → ⑤ 화면 계약과 픽스처 → ⑥ 구현 → ⑦ 검수 → ⑧ 적용과 기록. 화면이 읽는 것은 **화면 계약**(화면마다의 읽기 전용 데이터 꼴)뿐이다. 계약을 만드는 일은 화면마다 하나의 **어댑터**가 맡고, 시스템은 어댑터만 맞추면 된다. 그래서 화면 줄과 시스템 줄이 서로를 기다리지 않는다.

**차례.** **성장 선택과 첫 화면 겸 캐릭터 선택이 공동 1순위**이고, 두 화면이 하네스의 첫 적용 사례다(4.2절, 8절). 그 뒤 결과·전투 기록 → 스킬 트리(구성안까지, 구현은 D12 뒤) → 장비 → 전투 HUD의 부분 → 나머지.

**새로 만들 것은 다섯**(6절): 계약 검사기, 시안 장면 캡처(scene_shot 넓히기), 화면판 연속 캡처, 구성안 비교판, 픽스처 입력 검사. 구성안을 사용자가 고르는 화면은 **관리 툴의 「원화 시안」 화면을 그대로 쓴다**(묶음·후보·확정·메모가 이미 있다 [코드: `tools/manager/drafts.js` 43~78행, `tools/art/gallery.py` 5~7행]).

## 2. 하네스의 원칙 — 화면과 시스템의 분리선

### 2.1 분리선 한 줄

> **화면은 화면 계약만 읽는다. 시스템은 어댑터를 통해서만 화면에 닿는다. 화면은 무엇도 바꾸지 않고, 고른 것을 신호로만 내보낸다.**

```
[코어·저장·기록]  --읽기-->  [어댑터: <화면>_contract.gd]  --계약(Dictionary)-->  [화면: screens/<화면>.gd]
        ^                                                                              |
        +------------------------- 앱(chapter_one.gd)이 신호를 받아 코어에 요청 <------+
[픽스처 JSON]  --------------------------------------계약(Dictionary)-->  [같은 화면]   (검수·시안·검사)
```

- **화면 계약**: 화면 하나가 그리는 데 필요한 모든 값의 꼴. 글은 번역을 마친 문자열로, 수치는 전후 값으로, 색은 뜻 이름(`element:"frost"`, `grade:"rare"`)으로 담는다. 색 값·좌표·글꼴은 담지 않는다(그건 화면과 공통 바탕의 일). 판(版) 번호 `contract_version`을 단다.
- **어댑터**: 코어·저장·기록을 읽어 계약을 만드는 함수 하나(`static func build(run, ...) -> Dictionary`). 코어의 사적 필드(`_` 로 시작)와 내부 객체를 아는 곳은 여기뿐이다. 표현 쪽 파일이지만 화면 파일은 아니다.
- **픽스처**: 계약과 같은 꼴의 JSON. 상태 변형마다 한 벌(3.5절). 시안·구현·검수가 모두 이것으로 돈다.
- **신호**: 화면이 내보내는 것은 "카드 i를 골랐다", "다시 빌기를 눌렀다" 같은 뜻뿐이다. 코어에 요청하는 것은 앱이다(지금도 그렇다: `chapter_hud.gd` 12~15행의 `signal` [코드]).

### 2.2 무엇이 가능해지는가

| 상황 | 지금 | 하네스 뒤 |
|---|---|---|
| 시스템이 꺼져 있다(`run_spells.enabled=false`) | 화면 도구가 데이터 사본을 켜고 코어 사적 필드에 상태를 심어야 카드가 나온다 [코드: `scene_shot.gd` 259~298행] | 픽스처만 있으면 화면을 그린다. 켠 판의 실판 확인만 시스템을 기다린다 |
| 수치가 아직 안 맞는다 | 화면 검수가 수치 작업 뒤로 밀린다 | 화면은 "가장 긴 글", "가장 큰 수" 픽스처로 끝낸다. 수치는 시스템 줄의 일 |
| 시스템이 카드 id·필드를 바꾼다 | 픽스처가 깨진다(카드를 id로 풀에서 찾음, 287행) | 어댑터만 고친다. 계약이 바뀌면 판 번호를 올리고 화면 줄에 알린다 |

| 아직 없는 화면(마을, 상점) | 시스템이 생겨야 화면을 시작한다 | 시스템 **명세**가 서면 계약 초안으로 화면을 시작할 수 있다(코드는 기다리지 않는다). 설계 먼저 원칙(`CLAUDE.md`)은 그대로: 명세 없는 화면은 시작하지 않는다 |

### 2.4 분리를 지키는 규칙 다섯

1. 새 화면 파일(`chapter1/view/hud/screens/*.gd`)에는 `run`, `growth`, 사적 필드(`._`)가 나오지 않는다. 검사기가 센다(6절 T-1).
2. 화면은 계약을 받는 공개 함수 하나(`show(contract)` 또는 `apply(contract)`)와 신호만 가진다. 그 밖의 공개 진입점을 두지 않는다.
3. 계약의 필드는 화면이 그리는 것만. "혹시 쓸지 몰라" 넣지 않는다(읽지 않는 필드는 낡는다 — T7 3.6의 같은 원칙).
4. 어댑터는 코어를 읽기만 한다(`CLAUDE.md` "표현은 코어 이벤트와 읽기 전용 상태만"). 골든은 화면 줄에서 바뀌지 않는다.
5. 옛 층 메서드(`이름__q38` 등)에 층을 더하지 않는다. 화면을 다시 짓는 묶음은 그 화면의 옛 층을 정리하는 묶음이기도 하다(T1 4번과 순서를 맞춘다, 9절).

### 2.5 전투 HUD는 예외 조건이 있다

전투 HUD는 매 프레임 그린다. 계약을 매 프레임 Dictionary로 새로 만들면 비용이 든다[가설]. A4 3.2.5의 "HUD 동기화 +0.1ms 이내"를 지켜야 하므로, 전투 HUD의 계약은 **미리 만든 한 객체의 값을 매 프레임 덮어쓰는 꼴**로 하고 `frame_probe.gd`로 전후를 잰다. 이 판단은 qa-perf 측정 전에는 가설이다.

`PROCESS-CHECKS`의 다섯 문과의 관계: ①②③④는 문②(명세)의 안쪽, ⑤⑥은 문③(구현), ⑦은 문④(검수), ⑧은 문⑤(닫기)다. 화면 줄도 같은 말의 규칙("직접 봄 / 캡처만 있음 / 보지 않음", 모델의 답 표시)을 따른다.

### 3.1 ① 목적과 감정 — 화면 카드(brief) 틀

```
# <화면 id> <화면 이름> — 화면 카드
- 언제 뜨나 / 얼마나 자주(판당 몇 번, 근거 측정) / 판을 멈추나
- 플레이어가 이 화면에서 느껴야 할 것(한 줄, 동사로): 예 "셋 중 하나를 걸고, 고른 것이 내 것이 되는 순간을 본다"
- 키우는 사상(섹시·쾌감·도박·보상·성장)과 각각 어떻게(한 줄씩). 키우지 않는 것은 왜 아닌가
- 머무는 시간 목표(초)와 판 흐름에 주는 부담(예: D9 6.3의 판당 5.53초)
- 보여 줄 정보(위계 순서로): 반드시 / 있으면 좋음 / 넣지 않음
- 입력: 마우스·키보드·패드, 바로 고르기 키, 건너뛰기, 되돌리기
- 지키는 기존 결정: 사용자 결정, 명세의 절, 인물 규칙, 낱말 규칙(번호와 함께)
- 지금 화면의 캡처(두 해상도, 직접 봄/캡처만 있음)
- 시스템 쪽에 걸린 것: 꺼진 스위치, 명세 대기
```

"키우는 사상이 없는 화면은 뒤로 미룬다"(`CLAUDE.md`). 확인 창처럼 사상과 무관한 화면은 ①에서 "공통 바탕만 입힘"으로 닫고 ②~④를 건너뛴다(4.1의 "경로" 열).

### 3.2 ② 기준작 조사 — 무엇을 뜯어 보는가

편수: **같은 구실의 화면 3편 이상.** 둘은 같은 장르(군중 생존·ARPG), 하나는 장르 밖에서 그 감정을 잘하는 작품(예: 고르는 순간의 설렘이면 카드 뽑기 연출이 강한 작품). 조사의 재료는 녹화이고, 녹화 시각을 붙인다(`BENCHMARK-SACRATA-LOOP` 0절의 방식).

편마다 채울 여덟 항목:

| # | 항목 | 적는 법 |
|---|---|---|
| 1 | 구도 | 화면을 몇으로 나누나(예: 인물 1/3 + 카드 2/3), 그림과 글의 넓이 비 |
| 2 | 시선 흐름 | 처음·둘째·셋째로 눈이 가는 곳과 그 까닭(크기·밝기·움직임) |
| 3 | 위계 | 가장 큰 글자 / 가장 작은 글자의 비, 카드 한 장의 줄 순서와 줄 수, 글자 수 |
| 4 | 움직임과 시간 | 등장(초), 머무름, 고르는 순간(초), 퇴장, 건너뛰기. 프레임 시각으로 잰다 |
| 5 | 소리 | 등장·초점 이동·확정에 소리가 있나, 어떤 성격인가(녹화에 소리가 있을 때만. 없으면 "소리 없음"으로) |
| 6 | 입력 | 고르는 키, 다시 뽑기·제외, 확정이 한 번인가 두 번인가 |
| 7 | 감정 장치 | 기대 → 드러남 → 확정의 각 장치(예: 등급색 빛, 인물의 반응, 숫자가 오르는 연출) |
| 8 | 가져올 원리 / 베끼지 않는 선 | 구조와 원리만. 그림·이름·구도를 그대로 옮기지 않는다(`BENCHMARK-SACRATA` 4절) |

조사 문서 틀: 0. 재료와 한계(녹화 파일, 길이, 자막·광고로 가린 곳) → 1. 편마다 여덟 항목 표 → 2. 편끼리 같은 것과 다른 것 → 3. 우리 화면(① 캡처)과의 차이 → 4. 구성안에 넘길 원리 목록(번호) → 5. 확인하지 못한 것. 표기는 [봄]·[잼]·[추정].

### 3.3 ③ 구성안 — 무엇으로 그리는가

**고른 것: Godot 시안 장면.** 손 배치도는 보조로만, HTML 목업은 쓰지 않는다. 생성 그림 시안은 "승인 필요"일 때만.

| 그리는 법 | 좋은 점 | 나쁜 점(이 프로젝트에서) | 판정 |
|---|---|---|---|
| **Godot 시안 장면** (`chapter1/tests/proposals/<id>/<안>.gd`, 계약 픽스처를 받아 그림) | 실제 글꼴(`Loc.font`), 색 토큰(`palette.gd`), 틀(`ui_style.gd`의 9분할·아틀라스), 살아 있는 초상, 셰이더를 그대로 쓴다. 1600×900 캔버스와 두 해상도가 실제와 같다. `scene_shot`·`hud_layout_check`가 그대로 돈다. 움직임을 연속 캡처로 볼 수 있다. **고른 안이 구현의 출발점이 된다** | 안 하나에 시간이 더 든다. 에이전트가 GDScript로 그려야 한다 | **채택** |
| HTML 목업 | 빠르다. CSS 움직임 | 글꼴·색·틀을 두 번 정의한다(`PROCESS-CHECKS` 0절 "마. 같은 값이 여러 곳에"). Godot 컨테이너 배치와 글 넘침이 다르다. 고른 뒤 버린다. 픽스처·검사 도구를 못 쓴다 | 쓰지 않음 |
| 손 배치도(회색 상자, 글 대신 줄) | 가장 빠르다. 구도와 시선 흐름만 겨룰 때 좋다 | 감정·움직임이 안 보인다. 사용자는 그림으로 판단한다 | 보조: ③의 첫 30분, 안끼리의 차이를 디렉터와 맞출 때. 사용자에게는 보이지 않는다 |
| 생성 그림 시안(Codex 등) | 분위기와 재질을 빨리 본다(A4 5절의 목업 12장이 그 예) | 배치가 실제와 다르다. 글이 깨진다. 구독·유료 여부를 매번 따져야 한다 | 재질·인물 분위기 참고에만. **승인 필요**로 디렉터를 거친다 |

시안 장면이 지켜야 할 것:
- 위치: `chapter1/tests/` 아래(내보내기에서 빠진다 [코드: `export_presets.cfg` 11·56·101행 `exclude_filter`에 `chapter1/tests/*`]). 제품 코드를 고치지 않는다. 공통 바탕(palette, ui_style)을 **읽기만** 한다. 공통 바탕에 없는 것이 필요하면 시안 안에 두고 ③ 문서에 "공통 바탕 후보"로 적는다.
- 뒤 배경: 그 화면이 실제로 뜨는 순간의 실판 캡처 한 장(예: 성장 선택은 판 시작 5초쯤의 전투 화면)을 깐다[가설: 런타임에 `Image.load_from_file`로 `_local/shots/`의 PNG를 읽으면 `.gdignore`와 무관하게 된다 — 확인할 것].
- 안끼리 **다른 축이 둘 이상**: 인물의 비중(없음 / 곁 / 주인), 공개 방식(한꺼번에 / 한 장씩 뒤집기 / 고른 뒤 드러남), 정보 밀도(그림 위주 / 줄 위주), 카드의 꼴(세로 카드 / 가로 띠 / 원형 배치), 등급·종류를 무엇으로 가르나(바탕색 / 테 / 띠). 같은 방향의 색만 다른 안은 안 하나로 센다.
- 안마다 낸다: 한 줄 콘셉트, 정지 캡처(두 해상도 × 보통·가장 긴 글), **고르는 순간의 연속 캡처**(0.1초 간격, 등장·초점 이동·확정), 다섯 사상 표, 새로 필요한 그림·소리(유료면 "승인 필요"), 계약에 더 필요한 필드(시스템 요청), 기준작 조사의 몇 번 원리를 썼나.

### 3.4 ④ 사용자 선택

- 디렉터가 `tools/art/gallery.py add --sheet`로 비교판(6절 T-4)을 묶음 "화면안 · <id>"에 올린다. 관리 툴 「원화 시안」 화면이 묶음을 "선택 대기"로 보이고, 사용자가 확정·보류·버림과 메모를 남긴다 [코드: `drafts.py` 188행 `waiting`, `drafts.js` 122~124행].
- 움직임은 정지판으로 못 고른다. 연속 캡처를 영상으로 묶을지는 6절 T-3에서 정한다. 그 전에는 연속 캡처를 한 장의 띠로 보인다.
- 사용자가 섞기를 말하면(“A의 카드 + B의 인물”) art-lead가 한 안으로 합쳐 같은 판에 한 번 더 올린다. 두 번째 판에서 사용자의 확인을 받은 것만 ⑤로 간다.
- 기존 사용자 결정(예: 재질 (나) 장정과 실, 전투 막대 A 배치)을 거스르는 안은 ③ 문서와 비교판에 "기존 결정 N과 다름"을 적는다. 고르는 것이 결정을 다시 여는 일임을 사용자가 알게 한다.

### 3.5 ⑤ 화면 계약과 픽스처

**순서의 주의.** 구성안(③)을 그리려면 픽스처가 먼저 있어야 한다. 그래서 ①에서 "보여 줄 정보"로 **계약 0판**(지금 데이터로 채울 수 있는 것만)을 만들고, ③의 안들이 필드를 더 요청하고, ⑤에서 고른 안에 맞춰 **1판**으로 닫는다.

계약 파일(`chapter1/view/contracts/<id>.contract.json`)의 꼴:

```
{ "screen": "growth_choice", "contract_version": 1,
  "fields": { "cards": {"type":"array","min":1,"max":4,"item":{ ... }},
              "rerolls_left": {"type":"int","min":0,"requested":"U-26 / 시스템 줄 S-?"} ... },
  "variants": ["normal","long","empty","max","first","last","shade","spells_on"],
  "signals": ["chosen(index)","reroll()","skip_intro()"] }
```

- `requested`: 지금 시스템이 주지 못하는 필드. 픽스처에는 가짜 값을 넣고, 어댑터는 비워 두고, 화면은 빈 값일 때의 모습을 가진다. 시스템 줄 장부에 한 줄로 올라간다.
- 글은 번역된 문자열로 담고(어댑터가 `Loc.t`), "가장 긴 글" 변형은 실제로 나올 수 있는 가장 긴 문자열을 쓴다(지어낸 벽글이 아니다 — `scene_shot.gd` 32~33행 규칙). 번역 대비 1.4배 변형은 T3의 가짜 언어 규칙을 따른다.

변형의 기본 묶음(화면마다 맞는 것만):

| 변형 | 뜻 |
|---|---|
| `normal` | 가장 흔한 상태 |
| `long` | 가장 긴 이름·설명·가장 많은 줄 |
| `empty` | 가장 적은 상태(카드 하나, 장비 없음, 기록 없음) |
| `max` | 가장 많은 수(카드 넷, 장비 칸 가득, 숫자 자릿수 최대) |
| 화면 고유 | 성장 선택이면 `first`(판 첫 은총), `last`(마지막 은총), `shade`(그늘 상태, D9 0절 2), `spells_on`(켠 판의 카드) |
| 해상도 | 모든 변형을 1280×720, 1920×1080 둘로. 스팀 덱(1280×800)은 A4 0.3절대로 앵커 점검이 필요한 화면만 |

### 3.6 ⑥ 구현

- 새 화면은 새 파일 `chapter1/view/hud/screens/<id>.gd`. `chapter_hud.gd`는 어댑터를 불러 계약을 넘기는 자리만 가진다. `chapter_hud.gd`를 건드리는 묶음은 한 번에 하나(A4 8.1 규칙 그대로).
- 어댑터 `chapter1/view/contracts/<id>_contract.gd`. 고른 시안 장면(`tests/proposals/<id>/<안>.gd`)이 화면 파일의 출발점이다. 시안은 적용 뒤 지운다(8단계).
- 작업 폴더에서 패치와 보고서로(`PROCESS-CHECKS` 문③). 꺼진 값에서 골든 불변.

### 4.2 차례의 까닭

1. **성장 선택** — 사용자가 가장 불만인 곳(U-26). 판당 11번 뜬다(D9 0절 1, 9판 측정) — 플레이어가 가장 많이 보는 판 밖 화면이다. 다섯 사상 중 도박·성장·섹시·보상 넷이 걸린다. 켠 판(run_spells)이 꺼진 채라 **분리의 효과를 가장 먼저 보여 줄 화면**이기도 하다.
1. **첫 화면 겸 캐릭터 선택**(공동 1순위) — 사용자가 시험판을 띄워 보고 바로 짚은 곳(U-30). 게임을 켤 때마다 처음 보는 화면이라 섹시(인물)와 성장(마녀의 레벨·포인트)의 첫 인상을 정한다. 지금 계약 꼴(`profile_state`, `character_views` Dictionary)에 가까워 ⑤가 짧고, 코어를 읽는 곳이 적다[코드: `scene_shot.gd` 203~215행은 코어 상태를 심지 않는다]. 그래서 성장 선택과 **서로 다른 종류의 첫 적용 사례**가 된다: 하나는 분리를 새로 해야 하는 판 안 화면, 하나는 이미 분리에 가까운 판 밖 화면.
2. **결과 + 전투 기록** — 판의 끝맛. 전투 기록은 이미 계약 꼴이라 하네스의 ⑤가 짧다. 결과 창은 사적 필드를 읽고 있어 분리의 둘째 연습이 된다.
3. **스킬 트리** — 사용자가 밋밋하다고 했다(`SACRATA-LOOP` 0절). D12가 트리를 원소별로 다시 짜므로, ①~④(목적·조사·구성안·선택)는 지금 하고 ⑤ 이후는 D12의 트리 모양이 정해진 뒤. 첫 화면에서 스킬 트리로 들어가는 단추의 자리는 title의 ③에서 함께 정한다.
4. (비움 — 0판의 4번이던 타이틀은 1로 올라갔다. 번호를 당기지 않는 것은 다른 문서가 이 번호를 인용할 때 헷갈리지 않게 하려는 것이다.)
5. **장비(판 안 비교·보관함·착용 창)** — 보상·도박. D12 장비 옵션 재설계 뒤에 계약이 선다. 보관함 단추는 지금 첫 화면에 있으므로 title의 ③에서 어디로 옮길지 함께 정한다.
6. **전투 HUD의 부분** — A 배치가 확정이고 성능 조건이 있다. 시스템 결정(보상 등급 S1, 리듬 표시)에 걸린 것이 많다.
7. **정지·확인 창·안내** — 사상과 무관. 공통 바탕만 입힌다(②~④ 생략).

화면 줄은 한 번에 **둘까지** 돌린다[가설: `chapter_hud.gd`를 동시에 건드리지 않는 규칙 때문에 셋 이상은 서로 기다린다]. 그래서 첫 바퀴는 **성장 선택과 첫 화면 겸 캐릭터 선택 둘**이다. ①~④(문서·시안)는 나란히 가고, ⑥(구현)은 `chapter_hud.gd`를 건드리는 순서를 디렉터가 정한다(9.2절). 계약이 짧은 첫 화면이 T-1~T-5를 먼저 써 보는 구실을 한다. 결과·전투 기록은 둘 가운데 하나가 ⑧에 닿으면 들어온다.

## 7. 이 방법을 다른 게임에도 쓰려면

**일반적인 것**(다른 게임에 그대로)
- 여덟 단계와 단계마다 남기는 것, 문서 틀(화면 카드, 조사 여덟 항목, 구성안 요건).
- 화면 계약 / 어댑터 / 픽스처 / 신호의 분리선과 다섯 규칙(2.4).
- 변형 묶음(보통·가장 긴 글·빈 것·최대·두 해상도), 자동 검사의 종류(계약·배치·대비·입력·움직임 길이·실판), 사람 검수의 말("직접 봄 / 캡처만 있음 / 보지 않음").
- 구성안은 실제 엔진의 시안 장면으로 그리고, 사용자가 고르는 판에 같은 배율로 놓는다는 것.
- 도구 중 인수만 바꾸면 되는 것: `hud_layout_check.py`(캔버스·최소 글자 크기가 인수 [코드: 290~299행]), `shot_review.py`, T-1, T-4.

**이 프로젝트 고유의 것**
- 다섯 사상(섹시·쾌감·도박·보상·성장)과 그 표.
- 1600×900 코드 캔버스, 720p 하한 코드 14, 전투 화면 가운데 60% 규칙.
- 재질 방향 (나) 장정과 실, `palette.gd`의 색 뜻, 계열 세 색, 전투 막대 A 배치.
- 인물 규칙(A3 1.3절, `BOON-SCREEN-FIGURE-RULES`)과 낱말 규칙(`wording-rules.json`).
- Godot·GDScript에 묶인 것: `scene_shot.gd`, `layout_dump.gd`, 내보내기 제외 경로.
- 기준작(사크라타, 디아블로 2 레저렉션).

다른 게임으로 옮길 때: 일반적인 절(2·3·6절의 틀)을 한 문서로 떼고, 고유의 것은 "프로젝트 설정"(캔버스, 최소 글자, 사상 목록, 기준작, 금지 낱말 파일 경로) 한 JSON으로 둔다. 그 분리는 이 하네스로 화면 둘을 끝낸 뒤에 한다(쓰기 전에 일반화하지 않는다).

## 9. 정할 것

### 9.1 사용자가 정할 것

1. **이 하네스를 받아들이는가.** 받아들이면 `CLAUDE.md`의 "먼저 읽을 것"에 한 줄, 화면 작업은 ①~⑧을 거친다.
2. **구성안을 Godot 시안 장면으로 보는 것**(3.3절)이 괜찮은가. 시안 하나에 드는 시간이 HTML·생성 그림보다 길다. 대신 고른 것이 그대로 게임이 된다.
3. **화면의 차례**(4.2절). 성장 선택과 첫 화면 겸 캐릭터 선택을 공동 1순위로 두는 것(디렉터 전달), 스킬 트리를 D12 뒤로 미는 것.
4. 구성안이 기존 결정(재질 (나), 전투 막대 A 배치, 인물 규칙)을 넘어서는 안을 내도 되는가, 아니면 그 안에서만 내는가.
5. 고르는 판에서 움직임을 무엇으로 볼지: 연속 캡처 띠로 충분한가, 짧은 영상이 필요한가.
6. 첫 화면에서 타이틀과 캐릭터 선택을 한 화면에 둘지 둘로 나눌지 — 미리 정하지 않고 구성안의 축으로 겨룬 뒤 고르는 것이 괜찮은가.

### 9.2 디렉터가 정할 것

1. 계약·어댑터·새 화면 파일의 자리(`chapter1/view/contracts/`, `chapter1/view/hud/screens/`)와 이름.
2. 화면 줄을 동시에 몇 개 돌릴지(권고 둘, 4.2절). 첫 바퀴 두 화면의 ⑥이 `chapter_hud.gd`를 건드리는 순서(권고: 계약이 짧은 첫 화면 먼저).
3. T1 4번(옛 층 정리)과의 순서: 성장 선택의 ⑥이 `_growth_cards38__q38` 층을 지우는 일을 겸해도 되는가.
4. T-1~T-5의 배정과 차례(6절). T-3의 영상 묶기(ffmpeg 사용 여부 [미확인: 이 기계에 있는지]).
5. 화면 줄이 시스템 줄에 올리는 요청 필드를 어느 장부에 둘지(지시 장부의 둘째 표 / 화면 목록 T-6).

## 10. 확인하지 못한 것

- **Godot를 돌리지 않았다.** 모든 캡처는 이미 있던 것이다. 판 포기 확인, 종료·저장 안 됨 확인, 저장 거부·새로 시작 안내, 우두머리 막대, 장비 알림·교체 제안, 짧은 알림, 살아 있는 초상은 이번에 보지 않았다. 판 포기 확인은 캡처만 있다.
- `scene-shot-first`의 캡처(11-19 14:17)는 그 뒤의 `chapter_hud.gd` 변경(마지막 커밋 11-19 23:31)을 담지 않았을 수 있다.
- 결과 창은 승리만, 1920×1080만 봤다. 1280×720 캡처는 이번에 열지 않았다.
- `chapter_hud.gd`의 `Color("…")` 58곳 가운데 토큰과 같은 값이 몇인지 세지 않았다.
- 전투 HUD의 계약을 매 프레임 만드는 비용(2.5절)은 재지 않았다.
- 시안 장면이 `_local/shots/`의 PNG를 런타임에 읽을 수 있는지(3.3절) 확인하지 않았다.
- 관리 툴 「원화 시안」이 화면안 묶음을 원화와 같은 꼴로 보일 때 불편한 점(예: 캐릭터 칸이 비는 것)이 있는지 돌려 보지 않았다.
- 키아트·움직이는 초상(A4 P0·P1)의 지금 진행 상태를 확인하지 않았다.
- 시험판 첫 화면 캡처(`rs0/rs-frost-1080/01-menu.png`)에서 초상 칸이 거의 검은 까닭(찍힌 순간의 문제인지, 화염 초상·살아 있는 초상의 문제인지)을 확인하지 않았다. 폴더 이름은 frost인데 초점과 이름은 화염 마녀다.
- 첫 화면 1280×720은 이번에 열지 않았다.
- 정지 화면으로 판단할 수 없는 것: 모든 화면의 움직임, 소리, 반복해서 볼 때의 피로. 이것들은 사용자 플레이로만 채운다.
