## 0. 한 장 요약

**S1에 들어가는 것**: 리듬(오프닝·맛보기 머리 포함, 버티기 끔) · 우두머리 국면(쉼의 필살기 포함) · 강림 · 번개 키트(번개 마녀만, 트리 전부 열림) · 옵션 굴림 · 판정 v2 · 드랍 천장.
**빠지는 것**: 주문 구성, 버티기, 운, 분출, 구운 움직임, 일제 사격, 정예·지키는 자리, 권능 블록.

가장 무거운 발견 셋:

1. **"켠 판"이 이미 두 벌이다.** 앱의 시험 이름(`boss_finale`)·`trial_docs`·`kit_docs`·골든 사례(`rhythm-c1`, `boss-finale`, `element-arc`)는 `TrialPace`(D19의 첫 값)로 리듬 값을 **덮어쓴다**. 그런데 content-balance의 측정(RC-A·BF-B·RC-B·번개 키트 140판)은 `measure_rhythm.gd`가 따로 만든 문서, 곧 **데이터 파일의 리듬 값 그대로**를 쟀다. 관문 처치 수가 365/975/540 대 550/1,300/680이고 레벨 표도 다르다. 사용자가 치게 될 판과 골든이 지키는 판은 아무도 잰 적이 없는 판이다. → S1은 **측정된 쪽(데이터 값)** 하나로 정의하고, 세 곳(앱·검사·측정)이 같은 정의를 읽게 한다(2절).
2. **번개 키트를 저장을 켠 채로 켜면 실제 저장의 번개 트리 투자가 지워진다.** 키트가 켜지면 프로필은 번개 마녀의 트리를 원소 트리로 바꿔 읽고, 옛 투자는 "불법 투자"로 되돌림 처리된 뒤 다음 저장에 쓰인다. 키트를 끄고 돌아가면 반대 방향으로 한 번 더 되돌린다. 키트를 판에만 켜고 프로필에 알리지 않으면 이번에는 빌드가 "Not this witch's tree"로 거절되어 판이 시작되지 않는다. → 저장을 켠 S1은 **실제 저장과 분리된 시험 계정 파일**로만 연다(2.4절, 디렉터 결정 1).
3. **장비 스위치 셋을 함께 켜는 길이 없다.** `trial_docs.gd`의 `enable_affix_rolls_problem`·`enable_pity_problem`·`enable_luck_problem`은 저마다 새 장비 표를 만들어 `run.loot`에 넣으므로 둘을 부르면 앞의 것이 조용히 사라진다. 판정 v2를 켜는 도우미는 아예 없다. 그리고 운을 빼면 옵션 굴림이 굴리는 운 줄(`luck_bps`, 5행, `core_reads: true`)이 **효과 없는 줄로 장비에 붙는다**(디렉터 결정 2).

## 2. 켜는 길 하나

### 2.1 이름

- 실행 인수 **`--chapter1-trial=slice`**. 창 제목 태그와 캡처 머리에 `slice`가 찍힌다.
- `slice`는 **혼자만 쓴다.** 다른 이름과 함께 오면 앱은 다른 이름을 버리고 경고 한 줄을 낸다(C8: `spells`·`grace`가 섞이면 번개 판이 시작되지 않는다).

### 2.2 S1 정의 — 한 곳

**새 파일 둘** (gameplay-systems, S1-A):

1. `chapter1/data/trial_slice.json` — S1이 데이터 파일 위에 얹는 값만 담는다. 형식은 고정 키(모르는 키는 거절):
   ```json
   {
     "schema_version": 1,
     "status": "S1 시험판. 출하 기본값이 아니다. 값은 [가설]",
     "tuning": {
       "rhythm": {"enabled": true, "opening": true, "trial": false},
       "boss_finale": true,
       "taste_crest": {"beat": "gi", "at_ticks": 6000, "count": 14, "arc_deg": 70},
       "off": ["grace", "elites", "extras", "loot_flow"]
     },
     "descent": {"enabled": true, "cost": [3000, 8000, 10000]},
     "element_kit": {"enabled_elements": ["arc"], "tree": "all"},
     "loot": {"affix_rolls": true, "pity": true, "upgrade_verdict": true, "luck": false},
     "run_spells": false
   }
   ```
   값의 출처는 2.5절. 수치는 이 파일에서만 바꾼다(코드에 박지 않는다).
2. `chapter1/app/trial_slice.gd` — 앱 층(제품 코드)에 둔다. 검사가 `app/`을 preload하는 것은 이미 있는 길이다(`trial_docs.gd` 11행 → `app/trial_pace.gd`). 공개 함수:
   - `static func tuning_doc() -> Dictionary`: `combat_tuning.json`을 읽어 위 `tuning`을 얹는다. **`TrialPace`를 부르지 않는다**(C1). `off` 목록의 블록은 `enabled: false`로 고정한다. 일제 사격 키는 넣지 않는다.
   - `static func descent_doc()`, `static func kit_doc()`(`enabled: true`, `enabled_elements`), `static func loot_tables() -> RefCounted`(장비 표 **하나**에 `set_affix_rolls`·`set_pity`·`set_verdict`·`set_luck`을 모두 건다 — C3).
   - `static func apply(run) -> String`: 위 넷을 `set_tuning`·`set_descent`·`set_element_kit`·`set_kit_open(tree)`·`run.loot =`로 넣고, `set_run_spells`에 **꺼진 문서**를 넣어 출하 파일이 나중에 켜져도 S1이 흔들리지 않게 한다(C8). 성공이면 `""`, 아니면 한 문장. 번개가 아닌 마녀는 `ElementKit.is_on_for`가 거짓이라 키트가 저절로 꺼진다 — 따로 가르지 않는다.
   - `static func use_for_profile() -> void`: `ElementKit.use_override(kit_doc())` 다음 `ChapterProfile.refresh_element_kit()`. **저장을 켠 시험 계정에서만** 앱이 부른다(2.4절). 프로세스 전체에 걸리는 값이므로 검사에서 부르면 끝에 `use_override({})`로 되돌린다.
   - `const NAME := "slice"`.

**세 곳이 이 하나를 부른다**:

| 곳 | 부르는 길 | 담당 |
|---|---|---|
| 앱 | `_apply_trial`에서 `slice`면 `TrialSlice.apply(run)`. 다른 시험 이름의 갈래는 타지 않는다 | ui-hud(S1-B, A0 묶음과 함께) |
| 검사·골든·캡처 | 새 `tests/support/slice_docs.gd`의 `enable_slice_problem(run)`이 `TrialSlice.apply`를 부른다. `trial_docs.gd`·`kit_docs.gd`는 **이번에 고치지 않는다**(ui-hud가 A0에서 고친다). `TRIAL_NAMES`의 `slice` 추가는 ui-hud가 A0에서 함께 한다 | gameplay-systems(S1-A) |

### 2.3 저장을 끈 판의 규칙

- `--chapter1-profile-off`와 함께면 지금 시험 이름의 규칙 그대로다. 저장을 쓰지 않는다. `--chapter1-boss-now`, `--chapter1-descent-cost=`가 먹는다.

## 4. 작업 쪼갬

파일이 겹치지 않게 나눈다. ui-hud가 곧 `app/chapter_one.gd`·`chapter_hud.gd`·`combat_bar.gd`·`hud_dump.gd`·`trial_docs.gd`·`kit_docs.gd`를 번개 키트 A0·A2·A3으로 고친다. **S1의 앱 쪽 일(`slice` 이름)은 그 묶음에 합친다.** 두 담당이 같은 파일을 같은 때에 고치지 않는다.

### 차례

```
S1-A (gameplay-systems) ───────────┐
A0·A2·A3 (ui-hud, 이미 배정 예정) ─┼─> S1-B (ui-hud, A0 묶음의 끝에 붙임) ─> S1-D (content-balance 측정)
                                   │                                       ─> S1-E (qa-perf 성능·캡처)
S1-C (gameplay-systems, 결정 1이 (가)일 때) ── S1-A 뒤, S1-B와 나란히(파일 안 겹침) ─> S1-C' (ui-hud, 앱 연결 한 줄 묶음)
```

- **병렬**: S1-A ∥ ui-hud A0·A2·A3(파일 겹침 없음). S1-C ∥ S1-B(겹침 없음 — S1-C는 `chapter_profile.gd`와 검사만).
- **직렬**: S1-B는 S1-A의 `trial_slice.gd`가 합쳐진 뒤. S1-D·S1-E는 S1-A·S1-B가 합쳐진 뒤. 사용자 공개는 S1-D의 안전 문(5절)과 6절의 반드시 막을 것이 끝난 뒤.

### S1-A — gameplay-systems (지시서, 그대로 전달)

> **목표**: 「한 판」 시험판(S1)을 한 곳에서 정의하고, 검사·골든·측정이 그 정의를 읽게 한다. 코어는 고치지 않는다.
>
> **읽을 것**: `docs/specs/T14-slice-s1-20261125.ko.md` 1절(C1·C3·C8·C12·C13·C18), 2.2절, 2.5절, 3절.
>
> **고칠 파일(이것만)**: 새 `chapter1/data/trial_slice.json`, 새 `chapter1/app/trial_slice.gd`, 새 `chapter1/tests/support/slice_docs.gd`, `chapter1/tests/golden_core.gd`(사례 둘), `chapter1/tests/golden/core_runtime*.json`(갱신), `chapter1/tests/measure_rhythm.gd`(`--slice`), `tools/dev/kit_batch.py`(`--preset slice`), `tools/dev/check_build.py`의 필수 목록(새 데이터 파일 한 줄), 새 검사 `chapter1/tests/test_trial_slice.gd`와 `run_all.py`의 등록 한 줄.
>
> **건드리지 말 것**: `chapter1/core/` 전부, `chapter1/app/chapter_one.gd`, `chapter1/app/trial_pace.gd`, `tests/support/trial_docs.gd`·`kit_docs.gd`(ui-hud가 고치는 중), `chapter1/view/`, 출하 데이터 파일의 `enabled` 값.
>
> **계약**:
> - `TrialSlice.apply(run)`은 `start()` 전에 부르고, 성공이면 `""`를 돌려준다. `TrialPace`를 부르지 않는다. 리듬 값은 데이터 파일 그대로다.
> - 장비 스위치는 **장비 표 하나**에 모두 건다. `luck`는 `trial_slice.json`의 값을 따른다(지금 false — 디렉터 결정 2를 따른다).
