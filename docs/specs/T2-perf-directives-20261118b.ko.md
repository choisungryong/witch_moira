## 디렉터용 요약

1. **"fresh"는 새로 만든 표시가 아니다.** 적이 화면에 처음 나오는 순간(액터 사전에 키가 없을 때)마다 센다. 일반 적은 이미 판 시작 전에 풀(무법자 144, 원거리 40, 돌격 40)에 만들어져 있고, 한 판 4,216개의 97%(약 4,070개)는 **풀에서 다시 꺼낸 것**(하나에 약 0.61ms), 약 150개는 **풀에서 처음 꺼낸 것**(꺼내기만 하나에 평균 3.0~6.9ms, 트리에 붙이기·첫 자세까지 약 6~7ms)이다. 풀이 모자라 새로 만든 경우는 0이다. 계측 문서 3절의 "일반 적은 미리 만들지 않는다. 미리 만들면 없어진다"는 틀렸다. A-3은 "미리 만들기"가 아니라 **처음 꺼낼 때의 비용을 판 시작 전으로 옮기기(예열) + 꺼내고 넣는 비용 줄이기**로 정했다.
2. **적 모델은 하나가 아니라 둘이다.** 근접(walker)은 `skeleton_outlaw/v02/skeleton_outlaw_merged.glb`(해골 무법자), 원거리·돌격·정예·최종 우두머리는 `chained_warden/v01/chained_demon_animated.glb`(Mophs 악마)를 크기·색·덧붙임으로 나눠 쓴다. 시험판 대상은 walker가 맞다(생성 비율 약 82%, 모델이 따로라 다른 적과 얽히지 않는다).
3. **"코어 틱 6.2ms"의 3분의 1은 코어가 아니다.** 틱 하나 = 코어 계산 4.1ms + 표현의 이벤트 소비 1.0ms + 자동 조작(QA 전용) 1.1ms다. 실제 플레이에는 자동 조작이 없으므로, 창 측정의 후반 프레임은 실제 플레이보다 약 2.2ms 무겁다.
4. 순서: A-1(HUD), A-2(효과), A-3(액터 풀), B-a(굽기 도구)는 **파일이 겹치지 않아 동시에** 코드 작업을 할 수 있다. 창이 필요한 측정은 하나로 묶어 한 번에 잰다(D절). B-b(게임에 붙이기)는 A-2·A-3이 커밋된 뒤, B-c(시험판 측정)는 그 뒤다. C-1(코어 틱 나누기)은 헤드리스라 창이 필요 없지만 창 측정과 같은 시간에는 돌리지 않는다.
5. 디렉터가 정할 것: 9절.

### 할 일

0. **센다(헤드리스, 창 없음).** 임시로 프레임마다 다음 수를 세는 코드를 넣고(끝나면 뺀다), 1.1절의 덤프 실행(화염)으로 후반 프레임당 평균을 기록한다: 이름표 글이 실제로 바뀐 횟수(넣기 전 값과 다를 때), `add_theme_*_override` 호출 수, `queue_redraw()` 호출 수, 위치·크기 쓰기 수. 조각별로 나눠 적는다. 이것이 전후 비교의 기준이다.
1. **한 번 계산하고, 다를 때만 넣는다.** 각 조각의 최종 값(글, 색, 위치, 막대 값)을 먼저 지역 변수로 만든 뒤 지난번에 넣은 값과 다를 때만 넣는다. 작은 도우미(예: `_set_text(label, text)`, `_set_font_color(control, color)` — 지난 색을 메타나 사전에 기억)를 이 파일 안에 둔다. 층 함수(`sync__q46` 등)가 앞 층이 넣은 글을 고쳐 쓰는 구조(`dash.text+=...`, `status.text=("위험 · "...)+status.text`)는 "최종 글을 만드는 함수 하나 + 마지막에 한 번 넣기"로 바꾼다. 최종 글은 지금 화면에 나오는 것과 글자 하나까지 같아야 한다.
2. **숨긴 옛 아래쪽 칸에는 쓰지 않는다.** 부모(`life_seal38.get_parent()`)가 숨겨져 있으면 `status`, `hp`, `xp`, `level38`, `life_seal38`, `dash`, 기술 칩에 쓰지 않는다. 숨김이 풀리는 경로가 지금 코드에 있는지 먼저 찾아 보고한다(없으면 쓰지 않는 것으로 충분하다. 있으면 풀리는 순간 한 번 전부 넣는다).
3. **위치는 한 번.** 알림 위치(607, 720, 1355)를 마지막에 한 번 계산해 다를 때만 넣는다. 결과 값은 지금 세 번 넣은 뒤의 값과 같아야 한다.
4. **다시 그리기는 바뀔 때만.**
   - 주인공 표식: `feet`, `crown`, `danger`가 지난번과 다를 때만 `queue_redraw()`.
   - 전투 줄: `sync`에서 그림에 쓰이는 값들로 "그림 열쇠"를 만든다. 생명 글, 생명·영혼 비율(1/512 단위로 반올림), 영혼 색·열쇠, 레벨, 칸마다 (랭크, 진화, 대기 비율을 1/120 단위로 반올림한 값, 표시 초 `"%.1f"`), 회피·물약 남은 초 `"%.1f"`와 대기 비율, 물약 수, 효과 띠 목록. 열쇠가 바뀌었을 때만 `queue_redraw()`. 생명이 `LOW_LIFE` 미만이면(맥박이 시간에 따라 바뀐다) 매 프레임 다시 그린다.
   - 반올림 단위가 화면에서 보이는 차이를 만들면 단위를 더 잘게 하고 그 값을 보고한다.
5. **스냅숏 한 번.** `run.growth.snapshot()`을 HUD 프레임당 한 번 만들어 `chapter_hud.gd`와 `combat_bar.gd`가 같이 쓴다(`combat_bar.sync`에 인수로 넘기거나 HUD가 만든 값을 읽게 한다). `snapshot()`은 코어 함수지만 읽기만 하므로 부르는 횟수를 줄이는 것은 코어 변경이 아니다.

### 하지 말 것

- 보이는 글·색·크기·배치·순서의 변경. HUD 손질(아래 "순서")은 이 단위가 아니다.
- `chapter1/core/**`, `chapter1/app/**`, 다른 HUD 파일(`ui_style.gd`, `skill_tree_panel.gd`, `flow_dialog.gd`) 수정. 옛 층 파일 수정.
- 6틱 간격처럼 **값이 바뀌었는데 늦게 넣는** 방식. 이 단위는 "같은 값을 다시 넣지 않기"만 한다.

### 통과 기준

1. 0단계의 수를 1~5 뒤에 다시 센다. 후반, 값이 하나도 바뀌지 않은 프레임에서: 글 바뀜 0, 테마 덮어쓰기 0, 위치 쓰기 0, 다시 그리기는 생명 맥박·재사용 대기 칸이 있을 때의 전투 줄 1회 이하. 프레임당 평균을 전후 표로 보고한다.
2. `hud_dump.gd` 덤프(주력 셋, 기본 시점 + `--notice-shots`): `visible: true`인 행은 전과 **모두 같다**. 다른 행은 숨긴 옛 아래쪽 칸 아래의 것뿐이어야 하고, 그 목록을 보고한다. `--scene` 덤프는 전과 해시가 같다(HUD는 3D를 건드리지 않는다).
3. 덤프 실행 세 번 스크립트 오류 0. 골든 불일치 0. `run_all.py --quick` 전부 통과.
4. 창 측정(D절의 묶음 측정에서 함께): 판 전체 p50 중앙값이 **2.0ms 이상** 줄고, 후반 `f_hud` 평균이 **0.5ms 이하**. 줄지 않으면 0단계 표와 함께 보고한다(화면이 같으므로 되돌리지는 않는다).
5. 움직임 확인: 창 실행 한 번에서 생명 30% 미만의 맥박, 재사용 대기 칸이 줄어드는 모습, 회피 대기 초가 바뀌는 모습을 직접 보고 적는다(자동 조작이 생명 30% 아래로 잘 내려가지 않으면 그렇게 적고 미확인으로 둔다).

### 순서(같은 파일의 다른 일)

HUD 손질(생명 구슬 밝기, 위쪽 이름표·우두머리 바·경로 모양)은 같은 두 파일(`combat_bar.gd`의 `_draw_bound`, `chapter_hud.gd`의 `_draw_boss_caps`·`_draw_route_marker`·`_sync_chrome`)을 고친다. **A-1을 먼저 끝내고 커밋한 뒤 손질을 시작한다.** 손질에서 새로 움직이는 그림(시간에 따라 바뀌는 빛 등)을 넣으면 전투 줄의 "그림 열쇠"에 그 값을 넣거나 매 프레임 다시 그리는 조건에 더한다. 손질 지시서에 이 한 줄을 넣는다.

## A-2 — 효과 갱신 정리(vfx-feel)

### 목적

효과·타격 연출 갱신(후반 1.75ms + 엔진 쪽 약 0.5ms)을 줄인다. 앞 지시서 T2-3의 2~5번(다시 읽어 고쳐 쓰기, 빈 즉시 메시, 카메라 한 번, 정렬)은 이미 코드에 들어가 있다(`chapter_effects.gd` 241~247·368~386·585~594행의 "one write", 271~327·404~409·676~682·877~883행의 빈 표면 건너뛰기, 1122~1128행의 카메라, 1007~1010행의 정렬). 남은 것을 한다.

### 고칠 파일

`chapter1/view/fx/chapter_effects.gd`, `chapter1/view/fx/combat_juice.gd`만.

### 할 일

1. **MultiMesh 일괄 쓰기.** 지금은 인스턴스마다 `set_instance_transform`/`set_instance_color`/`set_instance_custom_data`를 따로 부른다. 묶음마다 `PackedFloat32Array` 버퍼 하나를 두고(인스턴스당 칸 수 = 변환 12 + 색 4(`use_colors`) + 사용자 데이터 4(`use_custom_data`)), 값을 채운 뒤 `RenderingServer.multimesh_set_buffer(multimesh.get_rid(), buffer)`를 한 번 부른다. 변환 칸 순서는 `basis.x.x, basis.y.x, basis.z.x, origin.x, basis.x.y, basis.y.y, basis.z.y, origin.y, basis.x.z, basis.y.z, basis.z.z, origin.z`다. 버퍼 크기는 `instance_count` 전체이고 `visible_instance_count` 뒤의 칸은 지난 값을 그대로 두어도 된다. 대상과 위치:

   | 묶음 | 위치 | 후반 인스턴스 수(어림) |
   |---|---|---|
   | 접지 그림자 | 206~220 | 적 수 + 1(약 100) |
   | 탄 + 냉기 대체 탄 | 221~253 | 수백, 인스턴스마다 3번(냉기면 6번) |
   | 영혼 구슬 | 254~262 | 수십 |
   | 충격·불기둥 + 냉기 대체 | 334~387 | 최대 48 |
   | 파편(`shards`) | 433~455 | 최대 960, 인스턴스마다 2번 |
   | 접촉 + 냉기 대체 | 568~598 | 최대 96 |
   | 얼음 | 755~771 | 최대 96 |
   | 얼음 조각 | 773~786 | 최대 128 |
   | 기절 불꽃 | 1011~1021 | 최대 144 |
   | 냉기 시전 | 1147~1156 | 최대 96 |
   | `combat_juice.gd` 불꽃 | 476~492 | 살아 있는 것만 |

   `combat_juice.gd`의 불꽃은 살아 있는 칸만 고쳐 쓰는 구조라 버퍼를 묶음 전체로 들고 있다가 바뀐 칸만 고치고 끝에 한 번 넣는다.
   **값과 계산 순서는 그대로 둔다.** 같은 `Transform3D`를 버퍼에 옮겨 쓰는 것이라 장면 덤프의 값이 같아야 한다.
2. **떨어진 아이템 이름 정렬.** `sync__q26`의 정렬 비교 함수(886~889)가 비교할 때마다 사전을 새로 만든다. 사전을 상수로 올린다. 결과 순서는 같아야 한다.
3. **빈 묶음 숨기기(실험, 효과를 재고 정한다).** `visible_instance_count`가 0인 MultiMeshInstance3D와 더미 정점만 든 즉시 메시 노드를 `visible=false`로 두고, 그릴 것이 생기면 켠다. 계측에서 "효과 노드 숨김 + 갱신 끔"이 "갱신 끔"보다 p50을 1.8ms 더 줄였다(한 회). 그 몫이 빈 묶음에서 오는지, 그려지는 효과에서 오는지는 모른다. 장면 덤프의 `visible` 칸이 바뀌므로 바뀌는 행 목록을 보고한다. 창 측정에서 효과가 없으면 이 항목은 되돌린다.
4. **피해 숫자 흐려짐(실험).** `combat_juice.gd` 471~474행은 흐려지는 동안 `Label3D`의 `modulate`와 `outline_modulate`를 매 프레임 바꾼다. `Label3D`는 이 값이 바뀌면 글자 메시를 다시 만든다(엔진 동작, 추정). 대신 `GeometryInstance3D.transparency`(=1−알파)로 흐리게 하고 `modulate.a`=1, `outline_modulate.a`=.9를 고정하는 방식을 시험한다. 글자와 테두리의 알파가 같은 비율로 곱해지므로 이론상 같은 결과다. 같은 시드의 창 캡처(흐려지는 순간 3장)를 전후로 나란히 보고, 다르게 보이면 되돌린다.

### 하지 말 것

색·크기·수명·상한·셰이더 변경. 효과의 종류나 개수 변경. 코어·데이터·`chapter1/tests/**` 수정. `chapter_actors.gd` 수정. 옛 층 파일(`chapter1/view/cloister_effects.gd` 등) 수정.

### 통과 기준

1. 장면 덤프(`--scene`)와 보조 동등성 덤프(`eq_dump.gd`) 주력 셋: 1번·2번만 한 상태에서 전과 해시가 같다. 헤드리스에서 MultiMesh 값을 읽지 못하면(모든 인스턴스가 단위 행렬로 나오면) 그렇게 보고하고, 측정 창 안에서 창 실행으로 같은 비교를 한다. 3번·4번은 바뀌는 칸 목록을 따로 보고한다.

## A-3 — 적 표시 풀: 처음 꺼냄 예열과 꺼내기·넣기 줄이기(refactor-architect)

### 목적

0.1절의 판정대로, 무리 등장 때의 튐 가운데 **처음 꺼냄**(판당 약 150개, 하나에 약 6~7ms, `actors.sync` 40ms 초과 프레임의 절반)을 판 시작 전으로 옮기고, **다시 꺼냄**(0.61ms)과 **돌려넣기**(0.28ms)를 줄인다.

### 고칠 파일

`chapter1/view/actors/chapter_actors.gd`만. 측정용 계측은 사본에서만 한다(`_local/perf/20261118-t2-fixed/tools/patch_actors.py`를 복사해 쓴다).

### 할 일

1. **예열.** `setup__q25b`(1219~1245) 끝, 또는 `setup()`(1556)의 끝에서 풀의 모든 일반 적 표시(무법자·원거리·돌격)와 정예·우두머리를 꺼내기 경로(`_create__q25b` 1263~1290의 꺼내기 → `view.add_child` → 첫 `_update_pose`와 같은 샘플링 → `_stash25`)로 한 번씩 돌린다. 두 가지를 차례로 재고 정한다.
   - (W1) 스크립트만: 위 경로를 메뉴 전에 돈다.
   - (W2) W1 + 한 번 그리기: 꺼낸 표시들을 카메라 안(메뉴 화면 뒤)에 한 프레임 보이게 둔 뒤 넣는다. 메뉴 화면에 비치는지 캡처로 확인한다.
   W1로 처음 꺼냄의 비용이 1.0ms 이하가 되면 W1에서 멈춘다. 예열 뒤 풀 표시의 상태(메타, 재생기의 클립과 위치, 뼈, 재질 색)는 예열 전과 같아야 한다(꺼낼 때 어차피 초기화하지만, 덤프가 숨긴 풀 노드도 기록하므로 같게 둔다).
2. **꺼낼 때의 쓸데없는 샘플링 빼기.** `_create__q25b` 1286행의 `stop(); play("idle",0); seek(0,true); advance(0)`은 바로 이어지는 첫 자세(`_pose_due`가 `first`라 반드시 돈다)가 다시 샘플링한다. 첫 자세 뒤의 뼈 값이 같다는 것을 보조 동등성 덤프로 보일 수 있으면 뺀다. 같지 않으면 빼지 않고 이유를 보고한다.
3. **트리 옮기기 대신 숨기기(측정 뒤 정함).** 지금은 꺼낼 때 풀 뿌리에서 떼어 `view`에 붙이고(`remove_child`+`add_child`), 넣을 때 반대로 한다(1259~1260, 1267). 표시를 처음부터 `view` 아래에 두고 `visible`과 `process_mode`만 바꾸는 방식으로 바꿨을 때 꺼냄·넣기 비용이 얼마 주는지 사본에서 잰다. 하나당 0.2ms 이상 줄면 반영한다. 장면 덤프의 노드 경로가 바뀌므로 동등성은 보조 동등성 덤프(키별 비교)로 본다. 계측 문서 2절의 "적 표시 풀을 트리에서 떼는 것은 이득이 없었다"는 풀 뿌리 전체를 떼는 실험이라 이것과 다르다.

### 하지 말 것

풀 크기 변경(모자란 적이 없다). 자세 갱신 일정(T2-2′) 변경. 그림자·재질·색 변경. 코어·데이터 수정. 등장을 다음 프레임으로 미루는 것(코어에 있는 적이 화면에 없는 프레임이 생긴다).

### 통과 기준

1. 보조 동등성 덤프 주력 셋: 모든 시점에서 **보이는** 액터의 상태가 전과 같다(1번의 예열로 숨긴 풀 노드가 달라지면 그 칸 목록을 보고한다). 3번을 반영했으면 노드 경로 차이 외에는 같다.
2. 덤프 실행 세 번 스크립트 오류 0, 골든 불일치 0, `run_all.py --quick` 통과.
3. 사본 계측(창, D절 묶음에서 함께, 기준과 번갈아 각 3회):
   - 처음 꺼냄 하나당 비용(꺼내기 경로 + 트리에 붙이기 + 첫 자세) **1.0ms 이하**(지금 약 6.8, 다시 꺼냄은 0.61).
   - 꺼냄이 있는 프레임의 `actors.sync` 평균이 꺼냄이 없는 프레임보다 **4ms 이하로만** 크다(지금 처음 꺼냄 프레임 23.5~26.0 대 4.2, 다시 꺼냄만 있는 프레임 12.3~13.2 대 4.2).
   - 10초 뒤 `actors.sync` 40ms 초과 프레임 가운데 꺼냄이 있는 프레임이 회당 **3개 이하**(지금 회당 약 8.6개).
   - 메뉴에서 판 시작까지의 시간이 늘어난 만큼(예열 비용)을 적는다. 1초를 넘으면 디렉터에게 묻는다.
4. 0.1절대로 가장 큰 튐(200ms 넘는 것)은 꺼냄 비용이 아닐 수 있다. 이 단위의 합격 조건에 넣지 않는다. 남은 큰 튐은 프레임별로 목록을 만들어 보고한다.

## B. 적 표시 구조 변경 시험판 — 정점 애니메이션 텍스처 + MultiMesh, walker 한 종

### B-1 대상: walker(해골 무법자)

- 수가 가장 많다(일반 적의 약 76~82%). 계측 T2-0b 표 B에서 프레임당 `seek`의 3분의 2가 walker다.
- 모델 파일이 따로라(0.2절) 원거리·돌격·정예·우두머리와 얽히지 않는다. 시험판을 접어도 다른 적은 그대로다.
- 덧붙임이 없다(원거리의 지팡이, 정예의 어깨 장식 같은 별도 노드가 없다). 몸과 도끼가 한 메시다.

### B-2 설계

#### 굽는 도구: Godot 안에서, 헤드리스로 굽는다

#### 텍스처 형식과 크기(어림)

- 위치: `Image.FORMAT_RGBAH`(16비트 실수), 가로 = 정점 5,375, 세로 = 약 191 → 약 8.2MB. 모델 좌표가 ±2 안이라 16비트 실수의 오차는 약 1mm 이하다.

- 합계 약 12MB(60fps면 약 25MB). 가로 5,375는 Godot의 최대 16,384 안이다.

- 메시의 `custom_aabb`는 모든 구운 프레임의 최소·최대로 둔다(공격·쓰러짐이 휴지 자세 밖으로 나간다).

### B-4 재는 법과 통과 기준

- 같은 커밋의 사본 하나에서 스위치 끔·켬을 번갈아 잰다. 1.2절 조건(시드 11, 화염, 300초, 1080p 창, 수직 동기 끔, 자동 조작). 측정기 인수 뒤에 `--chapter1-vat-walker`를 붙이면 켠 회차다.

- 지금 기준값(참고, `16c0c86` + 계측): 후반 `f_act` 8.1~8.4ms, 후반 other 약 9.9ms, 판 전체 p50 13.1~13.9ms.
- 회차별 값의 중앙값으로 판정한다.

| 판정 | 조건(모두 만족) |
|---|---|
| **넓힌다** | ① 후반 `f_act`가 **3.0ms 이상** 준다 ② 후반 `f_act` + other가 **3.5ms 이상** 준다(그리기 쪽에서 되돌려 받지 않았다) ③ 판 전체 p50이 **2.0ms 이상** 줄고, 켠 5회의 p50 최댓값이 끈 5회의 최솟값보다 작다 ④ 후반 GPU 시간(`f_rgpu`)이 **1.0ms 넘게** 늘지 않는다 ⑤ art-lead가 같은 시드 캡처에서 받아들일 수 있다고 판정한다 |
| **접는다** | 후반 `f_act` + other의 감소가 **1.5ms 미만**, 또는 GPU 시간 증가가 CPU 감소보다 크다, 또는 ⑤에서 고칠 수 없는 차이가 나왔다 |
| 보류 | 그 사이. 구간별 표와 함께 디렉터가 정한다 |

- p95·p99·50ms 초과 수는 범위로 함께 적는다. 틱 밀림이 풀리면 p95가 p50보다 크게 줄 것으로 본다(추정)이지만 기계 흔들림 때문에 합격 조건으로 쓰지 않는다.
- 어림(근거: T2-fixed의 후반 `actors.sync` 약 8.3ms 가운데 자세 4.7ms, walker가 자세 호출의 약 3분의 2, 나머지 액터별 일 약 3.6ms의 3분의 2): `f_act` −3.5~−4.5ms, other −1~−2ms. 보장이 아니다.

4. 표현 쪽 틱당 일의 몫(`effects`/`juice`/`actors`/소리/장 이벤트).
5. 자동 조작(QA 전용) 틱당 시간. 실제 플레이와 측정의 차이를 이 값으로 적는다.

## 9. 디렉터가 정할 것

1. **시험판의 화면 차이를 어디까지 받을지.** 피격 상체 섞기가 정점 근사로 바뀐다. 먼 walker가 매 프레임 움직인다(지금보다 부드럽다). 걷기는 30fps로 구워 보간한다. 이 셋을 B-b 캡처와 사용자 플레이로 판정한다는 것을 사용자께 미리 알릴지.
2. **넓히기로 정했을 때 구운 결과물(약 12~25MB)을 저장소에 넣을지, 판 시작 전에 구울지.** B-a의 굽는 시간을 보고 정한다.
3. **A-1의 숨긴 옛 아래쪽 칸.** 쓰지 않게 하면 `hud_dump.gd` 덤프의 숨김 행 값이 달라진다. 이 차이를 받을지, 아예 그 칸을 없앨지(없애면 덤프의 행 수가 바뀐다).
4. **A-2의 실험 두 개(빈 묶음 숨기기, 피해 숫자 흐려짐 방식)를 측정으로 정해도 되는지.**
5. **측정 조건의 자동 조작.** 모든 창 측정에 자동 조작이 틱당 약 1.1ms(후반 프레임당 약 2.2ms) 들어 있다. `docs/QUALITY-TARGETS.ko.md` 1절의 p95 16.6ms를 자동 조작이 있는 측정으로 판정할지, 자동 조작 시간을 뺀 값으로 판정할지.
6. **A-3 예열이 판 시작을 늦추는 시간의 상한**(제안 1초).

사용자께 여쭐 것은 1번(화면 차이를 사용자 플레이로 판정한다는 것)과, B-5 요약에 대한 확인(새 적은 수가 많은 일반 적만 새 방식으로 만들고 우두머리는 지금 방식으로 둔다)이다.
