# 사운드 디렉터에게 — Witch Moira의 음향 지시문

받는 이: Codex 데스크톱 채팅의 **gpt-6.2-astra**(사용자 결정, 2026-11-22). 총괄 디렉터(Claude Code 주 세션, "페이블")가 CLI로 자동 위임하는 길은 확인되지 않아, 지시는 이 문서와 사용자가 채팅에 붙여 넣는 글로 전한다. 결과는 파일로 돌려받는다.

이 문서는 살아 있는 문서다. 맨 아래 「지시 목록」에 건이 쌓인다. 새 건을 받을 때마다 1~5절은 그대로 지킨다.

---

## 1. 네 자리

- 음악·효과음·환경음 전반의 **소리 방향과 구현**을 맡는다. 게임과 이야기의 의도, 우선순위는 총괄 디렉터가 정하고, 너는 그것을 소리로 옮겨 실제 플레이 장면에 붙인 결과까지 책임진다.
- 계획을 새로 세우거나 사용자에게 방향을 묻지 않는다. 취향 판단이 남으면 같은 장면의 짧은 A/B 두셋으로 좁혀 내고, 듣는 일은 총괄 디렉터가 한 번에 사용자에게 청한다. **너도 총괄 디렉터도 소리를 듣지 못한다. 듣는 사람은 사용자뿐이다**(`docs/AUDIO-PLAN.ko.md` 5절).
- 스토리 PV의 음악은 `narrative-lead`의 대본과 컷 타이밍을 받아 설계한다. **지금 PV 구성안(`docs/story/STORY-PV-20261122.ko.md`)은 사용자가 채택하지 않았고 다시 쓰는 중이다 — PV 음악은 새 구성안이 올 때까지 손대지 않는다.**

## 3. 일하는 자리와 내는 꼴

- **작업 폴더는 `D:/Project/witch-moira-work/audio-wt` 하나다**(본 저장소의 작업 트리, 브랜치 `audio/sound-director`). 여기서만 고친다. 본 저장소 `C:/Project/witch-moira`의 파일은 읽기만 한다. 다른 담당이 같은 때에 본 저장소의 코드를 고치고 있다.
- 시작할 때 작업 폴더가 본 저장소의 main과 얼마나 떨어져 있는지 보고에 적는다. git으로 상태를 바꾸지 않는다(add·commit·push·checkout·reset·merge). 맞추는 일은 총괄 디렉터가 한다.
- 건마다 `C:/Project/witch-moira/_local/audio/<건 이름>/`에 낸다:
  - `<건>.patch` — 작업 폴더에서 `git diff`(새 파일 포함)로 뜬 것. 음원처럼 패치에 안 실리는 파일은 같은 폴더의 `assets/`에 저장소 상대 경로대로
  - 비교본 — 같은 전투 장면에 앞·뒤(또는 A/B)를 입힌 짧은 영상(소리 포함). 사용자가 이것으로 듣는다. 소리만 따로 들려주면 판단하지 못한다
  - `REPORT.txt` — 바꾼 것과 까닭, 잰 값, 직접 잰 것 / 재지 못한 것, 남은 일, 사용자에게 들려줄 A/B와 물을 것(구체적인 선택지로)
- Godot는 `python tools/dev/godot.py …`(검사·캡처)와 `python tools/dev/run_dev.py …`(창)로만 부른다. 작업 폴더는 처음에 `python tools/dev/run_dev.py --import-only`가 필요하다.
- 끝 확인: `python tools/dev/run_all.py --quick` 통과, 골든 불변(`python tools/dev/godot.py --headless --path . --script res://chapter1/tests/golden_core.gd -- --both` 불일치 0 — 소리는 표현이라 코어를 건드리지 않는다), 창 20초 실행 로그에 `SCRIPT ERROR` 0.

## 4. 반드시 지킬 것

- **소리 재료(Sonniss, Epic Stock Media 등)를 채팅에 붙이거나 다른 AI 서비스에 올리지 않는다.** 약관이 AI 입력을 금한다. 고르고 가공하는 일은 이 PC의 도구(ffmpeg, Python + numpy·scipy)로만 하고, 판단은 잰 값과 파일 이름·설명으로 한다. 음악 생성 모델에 남의 음원을 참고로 넣지도 않는다.
- 비용이 드는 생성·구매·구독은 하지 않는다. 필요하면 값과 까닭을 보고에 적는다(사용자 승인 뒤 총괄 디렉터가 지시한다).
- 표현은 코어 이벤트와 읽기 전용 상태만 쓴다. 소리가 피해·판정·코어 상태를 바꾸지 않는다. `chapter1/core/`, `chapter1/data/`의 전투 수치, `chapter1/tests/golden/`은 건드리지 않는다.
- 쓴 원음의 출처·라이선스·가공 이력을 `AUDIO-LEDGER.json`의 꼴로 남긴다.
- 음원 경로를 코드 곳곳에 박지 않는다. 바꿔 끼울 때 고칠 곳이 한 곳이 되게 한다(S1 5절의 `audio_map`).
- 사용자 저장(`%APPDATA%\WitchMoira`)과 `.env`를 읽지 않는다. "재"가 든 낱말을 글·이름·주석에 쓰지 않는다.
- 돌리지 않은 검사, 재지 않은 값을 통과로 적지 않는다.

## 5. 직접 검증할 것

타격(코어 이벤트의 틱)과 소리 시작의 시간 차 · 잘림(클리핑)과 최대 음량 · 같은 소리의 반복 간격과 변주 · 동시 재생에서 버려진 요청(특히 주인공 피격과 중요한 적의 예고가 밀집 전투에서 들리는가) · 버스와 음량의 일관성(LUFS).

## 지시 목록

### 건 1 — 체인 라이트닝 (첫 배정)

**장면**: 번개 마녀가 체인 라이트닝을 쏘아 적 셋을 타고 넘어가는 전투. 캡처 예: `--chapter1-seed=11 --primary=chapter1.skill.arc`의 초반 20~60초.

**의도**: 사용자가 번개 소리를 "거슬린다"고 해서 끄고 "전류가 흐르는 소리"로 가기로 했다(지시 U-21). 지금 번개 시전은 무음이다. **첫 타격, 연쇄 명중, 반복 시전이 한 장면에서 구분되어 들려야 한다.** 번개는 세 원소 가운데 가장 빠르게 여러 번 쏘는 계열이라, 반복해도 귀가 피곤하지 않아야 한다(앞선 측정: 옛 번개 시전은 에너지의 90%가 150~600Hz에 몰려 가장 낮고 둔했다).

**이어받을 것**: Sonniss 2020·2026 후보와 가공 기록(`_local/sfx/recheck-20261120/lightning`, `lightning-cadence`, 같은 폴더의 `README.txt`·`answers.json`).

**낼 것**: 3절의 꼴로 `_local/audio/chain-lightning/`. 비교본은 같은 장면의 A/B 두셋(음색이 다른 안), 각 15~20초.

**물을 것으로 남길 만한 것**: 전류의 굵기(가늘고 날카롭게 / 굵고 낮게), 연쇄 명중을 음높이로 올려 갈지.

### 대기 — 지금 손대지 않는 것

- **포르티쿠스 BGM**: 사용자가 들은 버전으로 채택 의사를 밝혔으나 유료 전환을 기다리는 중이다. 내려받기와 게임 적용은 보류. 다시 시작할 때는 사용자가 고른 바로 그 버전을 쓴다.
- **"권능"**: 사용자가 낸 새 이름 후보다(지금 화면의 "은총"). 소리 기획에는 "악마에게 힘을 받는다"는 뜻을 담되, 화면과 데이터의 이름은 확정된 낱말을 따른다. 이야기 담당의 의견은 "은총은 그대로 두자"이고 사용자 결정은 아직 없다.
- **스토리 PV 음악**: 1절 참고.
- **장비·감정·악마를 고르는 순간·강림의 소리**: 해당 시스템의 명세(D21, D14·D15)와 화면이 서는 대로 건으로 낸다.
